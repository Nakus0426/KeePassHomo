## 1. 文档用途

本文用于确定 KeePassHomo 的开发顺序、阶段边界和完成条件，并通过 checkbox 跟踪工程进度。

- 产品需求、页面行为和视觉约束以产品设计清单为准。
- 本文只组织实施顺序，不取代产品设计清单。
- `[P0]` 是首版必须完成的范围；`[P1]` 只做自动填充能力验证；`[P2]` 不进入首版。
- 只有实现、构建验证和用户手动验收均完成后，任务才可勾选完成。

### 状态约定

- `[ ]` 未开始或未完成。
- `[x]` 已完成并满足本阶段退出条件。
- 受阻事项保持未勾选，并在“风险与决策记录”中说明原因，不把部分完成标记为完成。

## 3. 实施原则与依赖顺序

开发主路径：

```text
KDBX 技术验证与安全基础
  -> 本地保险库最小纵向闭环
  -> 完整本地密码库
  -> WebDAV 与离线同步
  -> 安全中心和完整设置
  -> 响应式、无障碍及 P0 收敛
  -> P1 自动填充能力验证
```

必须遵守以下约束：

- KDBX 文件是唯一数据真源，不建立不可导出的私有密码库格式。
- UI 不直接调用文件、密码学或网络接口，只调用明确的领域服务。
- 保存条目时必须先生成完整临时 KDBX，重新打开校验成功后再替换原文件。
- WebDAV 上传必须发生在本地保存成功之后，且上传前必须比较远端版本。
- 任何冲突、覆盖、永久删除、明文导出或凭据修改都不得静默执行。
- 先完成单条本地纵向流程，再横向扩展条目类型和页面，避免 UI 先行造成返工。
- 仅在系统边界校验输入和错误；内部模型信任类型与框架保证。

## 5. 阶段验收规则

每个阶段按以下顺序收敛：

1. 实现该阶段的完整纵向调用链。
2. 使用项目静态检查确认 ArkTS、性能和安全规则。
3. 使用 `devecocli build --product default --modules default@default --build-mode debug` 验证编译、资源和配置。
